# lib/field-notes (top level): exports for the spine wiring

Owner: orchestration core builder. Mirrors `lib/ai-events` file for file. Imports are `@/lib/field-notes/<file>`. Shared shapes stay in `types.ts` (`FIELD_NOTES_VERTICAL`, `FieldNotesSettings`, `Tip`, `Post`, `Slide`, ...). Tests: `npx tsx --test tests/field-notes-run.test.ts` (offline, PGlite).

## What the worker wires (G)

```
claimRun(q) -> carryOutFieldNotesRun({query, now, log, engine: (run, cap) => liveFieldNotesDeps(query, {capUsd: cap})}, run)
```
wrapped in `withFieldNotesTimeout(..., FIELD_NOTES_RUN_TIMEOUT_MS, () => fail the run)`. The clock: `noonQueue(now, await readFieldNotesSettings(q), await scheduledRunToday(q, nyDate))`, then `requestRun(q, 'scheduled', cap)`; it always says no while auto_run is false. Publisher: `releaseDueFieldNotes(query, {requireApproval})` and `claimAndPublishFieldNotes(deps)`, only while `publishingLive`. Hub actions: `queueManualFieldNotesRun`, `approveFieldNotesPost`, `rejectFieldNotesPost`, `unscheduleFieldNotesPost`, `hardPublishFieldNotesPost`.

## Run behavior (v2, 2026-11-05: one run = one post of 3-6 tips (TIP_SLIDES_MAX raised to 6 on 2026-11-08), one tip per slide; see planning/Field Notes/CONTRACT-v2.md)

The numbered list below is the v1 flow; where it says one tip, `writePost` now takes 3-6 tips (seeds first, then scored candidates only when questions are approved), slide 1 is a Faces photo (`checkPhotoPool` refuses a run with none), and `cover_no_face` swaps the cover for another Faces photo.


1. `max_pending_drafts` (review posts not yet approved or rejected on the spine): full -> run `skipped`, `stop_reason` `pending-drafts: ...`. `queueFieldNotesRun` refuses with the same limit.
2. Unused `candidate` tips older than `tip_expiry_days` become `expired` (the type's own housekeeping).
3. Tip: `claimed.seedTipId` (the form), else the oldest unused seed tip, else (only when `FIELD_NOTES_SOURCES_CONFIG.questionsApproved`) `collect` new candidates (public pages, no model), score only the tips this run just saved with Jev (never a candidate an earlier run left: Rule 2), and `selectTips`. Seeds go on in order under the same post rules (distinct subjects, at most two of one want: `sources/select` `admitSeeds`); the rest wait (`record.seedsWaiting`). No seed and not approved -> `skipped`, `stop_reason` `scoring-not-approved: ...`, nothing found or scored. A seeded tip is never scored.
4. At least 4 rested photos before any paid call (`photos-short` otherwise); `writePost` (Writer, Editor, gates); then exactly slides + 1 photos, newest upload first (`photos/pickPhotos`), the last one is the Follow slide's.
5. Render through the injected `renderPost`; `font_missing` is fatal (nothing stored); other problems are stored (`fit_problems`, `render_problems`) and the writer's soft notes go to `posts.soft_notes` (shown as Notes on the review screen; they never count as fit problems).
6. JPEGs to Storage (`field-notes/<slug>/v1/slide-NN.jpg`), the post row (review), then the photos rest (`recordUse` with the row's identity `seq`), the tip becomes `drafted`.
7. Spend: `claude_usd`, `jev_usd`, `total_usd` on the run row (the existing cost ledger reads `<type>.runs`); per-call detail in `record.spend.calls`. Stop reasons on the row: `pending-drafts`, `scoring-not-approved`, `no-tip`, `seed-unavailable`, `photos-short`, `cap`, `gate`, `write-failed`.

## Ingestion and dedup (F1, 2026-11-06)

- Found candidates: collect -> `dedupeCandidates` -> drop links already stored (`storedSourceUrls`, one lookup) -> `sources/select` `scoringOrder` (at most `MAX_CANDIDATES_PER_SOURCE` per source, newest first; `MAX_SCORED_PER_RUN` slots round-robin in registry order) -> only those slots enriched (`enrich`: README / linked page) -> Jev scores each -> saved only then, with score and tags. Unscored candidates are not saved, so a later run finds them again. No stored row is ever scored (Rule 2).
- `sources/candidate`: `canonicalSourceUrl` collapses a GitHub repo root, `/tree/<branch>`, `#readme`, `.git` and any query on the root to the lowercase `https://github.com/owner/repo`; deeper GitHub paths lowercase owner/repo only. `githubRepoOf(url)` -> `{owner, repo, slug}` \| null (the one GitHub repo parser; `slug` is lowercase `owner/repo`), `candidateTitle(c)` (first line of the scraped text, a dedupe key only).
- `sources/select`: `subjectKey` is a seed's subject, else the candidate's own normalized title (never the source label); `subjectKeys` adds `github:owner/repo`; `normalizeSubject`. `selectTips` input gains `takenUrls` and `minTotal` (the want cap relaxes just enough to reach it); posted subjects (normalized) and posted GitHub repos are skipped, and so is a candidate whose title or first `POSTED_NAME_HEAD_CHARS` (300) of text names one (`postedNames` / `namesPostedSubject`: a posted headline of 2+ words, a posted command or slug token, a posted `owner/repo`); `technique` tips never expire (`EVERGREEN_LEAF`).
- AI gate and post mix (G1, 2026-11-06; Tommy: "Yes, please fix all the problems you identified"): `sources/questions` is `field-notes-score@3` = @2 plus the `about_ai` noul (`ABOUT_AI_KEY`, `ABOUT_AI_THRESHOLD` 0.5); `questionsApproved` stays true. Score = weighted mean x WANT_WEIGHTS[want] x (about_ai >= 0.5 ? 1 : 0). `sources/select`: a 0 score is never eligible (not even to reach `minTotal`); `REPO_LEAVES` (the six `repo_*`), `MAX_REPO_TIPS` (2), `FEATURE_LEAVES` (`coding_agent_feature`, `llm_app_feature`, `technique`), `isRepoLeaf`, `isFeatureLeaf`; `selectTips` input gains `takenLeaves` (seeded tips' leaves: repo leaves count toward the cap, a feature leaf meets the feature rule). At most 2 repo tips per post; the best free feature tip takes the last slot when the post has none (it beats the want cap); inside WANT_TIE_BAND a feature tip goes first, then the least-used want; under `minTotal` the want cap relaxes first, then the repo cap. `run.ts` passes `takenLeaves`.
- Re-pay guards (`run.ts`): a Writer-skipped tip is rejected (`reject_reason` `writer-skipped: ...`); a tip that got a slide in a run that saved no post (gate, insufficient source, later failure) gets `recordTipAttempt` (set aside at 2). A paid write with no draft sets its tips aside as before. A saved post's tips get their slide headline as `subject`.
- Schema: `tips.attempts integer NOT NULL DEFAULT 0`, `tips.reject_reason text` (idempotent `ADD COLUMN IF NOT EXISTS`, no backfill).

## Deviations from ai_events

- No weekly clock, no `days`: `auto_run` ships off and `noonQueue` returns off; `FIELD_NOTES_AUTO_DAYS` (Tue, Fri) is a placeholder for when it is turned on.
- The run does not book a slot (ai_events books at run time while live). Booking happens on approval (`approveFieldNotesPost`), only while publishing_live is on, in the one `afternoon` window, any day, 30 minutes from other feed posts. Approving sets `posts.approved_by` and the tip `approved`; rejecting rejects the tip too; publishing sets the tip `posted`.
- `queueFieldNotesPublish` and `claimAndPublishFieldNotes` also check publishing_live themselves (defense in depth); ai_events leaves that to the worker.
- No snapshot publisher (ai_events publishes a public calendar).
- Claude IS used (Writer, Editor; ai_events uses none), so `finishRun` takes `claudeUsd` as lfd does, and the engine meters both clients itself (`budget.ts`); `live.ts` builds raw clients only.
- The seed rides in the run's `record` JSON (`seedTipId`), because `field_notes.runs` has no column for it; `claimRun` reads it back. `finishRun` overwrites `record` with the final record (which repeats `seedTipId`).
- `rebuild` runs are not supported: `queueFieldNotesRun` refuses, and a claimed rebuild finishes `skipped`.
- Caption closings: `social_hub.caption_closings` CHECK lists only carousel, reel, explainer, lfd, so the closing is NOT logged (SQL not edited). The caption is the Writer's text plus a fixed follow line and 4 hashtags (`caption.ts`). When the CHECK learns `field_notes`, log the closing from `run.ts` with `closingsLog(query, 'field_notes')`.
- Arrow marks are not placed: the planner needs a target point and there is no vision read of the photo's subject yet; the default look currently has the orange underline (hook headline's last two words) and step markers only.
- The Why and the Catch (lines one and two of the why_catch slide) are joined into the slide's one body as `Why: ... Catch: ...`.
